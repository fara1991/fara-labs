# 作者への報告とメンテナンス画面の設定（Cloudflare・Discord）

4 つのサイト（Pokémon Battle Assistant・Avatar Modding Guide・FaraBotModerator・Fara Labs）に共通の設定です。
コードの側（フッター・`/report`・`/privacy`・`POST /api/report`）は、各リポジトリに入っています。**ここに書いた設定をするまで、報告ページは「いまは報告を受け付けていません」と表示されます**（壊れてはいません）。

---

## 1. 作者への報告（Discord に通知する）

報告フォーム → サイトの Worker（`/api/report`）→ Cloudflare Turnstile で確認 → Discord に通知、という流れです。報告の内容は保存しません（Discord にだけ残ります）。

### 1-1. Discord の Webhook を作る

1. 通知を受けたい Discord のサーバー（自分用の小さなサーバーでよい）のチャンネルを選び、「チャンネルの編集」→「連携サービス」→「ウェブフック」→「新しいウェブフック」。
2. 名前を付けて（例: サイトの報告）、「ウェブフック URL をコピー」。
3. **この URL は秘密です。** 知られると、誰でもそのチャンネルに書き込めます。漏れたときは、そのウェブフックを削除して作り直します。
4. スマホで通知が欲しいときは、そのチャンネルの通知を「すべてのメッセージ」にしておきます。

### 1-2. Cloudflare Turnstile（ボット判定）を作る

1. Cloudflare のダッシュボード →「Turnstile」→「ウィジェットを追加」。
2. 名前: `fara sites report`、ホスト名に次の 8 つを追加します。
   - `pokemon.fara-labs.com` / `pokemon-dev.fara-labs.com`
   - `avatar.fara-labs.com` / `avatar-dev.fara-labs.com`
   - `twitch-bot.fara-labs.com` / `twitch-bot-dev.fara-labs.com`
   - `fara-labs.com` / `dev.fara-labs.com`（このポートフォリオ。フッターの「作者へ報告」を送る先）
3. ウィジェットのモードは「Managed（管理）」にします。作成すると、**サイトキー**（公開してよい）と**シークレットキー**（秘密）が表示されます。

### 1-3. 8 つの Worker に値を登録する

Cloudflare のダッシュボード →「Workers & Pages」→ 次の Worker を 1 つずつ開き、「設定」→「変数とシークレット」→「追加」で、下の 3 つを登録します（**種類は 3 つとも「シークレット」**にしてください。理由は下の注意）。

| Worker | サイト |
| --- | --- |
| `fara-pokemon` | https://pokemon.fara-labs.com/ |
| `fara-pokemon-dev` | https://pokemon-dev.fara-labs.com/ |
| `fara-avatar` | https://avatar.fara-labs.com/ |
| `fara-avatar-dev` | https://avatar-dev.fara-labs.com/ |
| `fara-twitch-bot` | https://twitch-bot.fara-labs.com/ |
| `fara-twitch-bot-dev` | https://twitch-bot-dev.fara-labs.com/ |
| `fara-portfolio` | https://fara-labs.com/ |
| `fara-portfolio-dev` | https://dev.fara-labs.com/ |

| 名前 | 値 |
| --- | --- |
| `TURNSTILE_SITE_KEY` | Turnstile のサイトキー |
| `TURNSTILE_SECRET` | Turnstile のシークレットキー |
| `DISCORD_WEBHOOK_URL` | 1-1 でコピーした Webhook の URL |

> **注意（種類は「シークレット」）**: この 3 つは、中身を画面に表示しない「シークレット」にします（Webhook の URL とシークレットキーは、他人に見えてはいけない値です。サイトキーは公開してよい値ですが、そろえておきます）。メンテナンスの変数（`MAINTENANCE_MODE` など）は、あとから値を見て書き換えるので「テキスト」にします。どちらも、公開（`wrangler deploy`）では消えません。

### 1-4. 動作を確かめる

1. 確認用のサイト（例: https://pokemon-dev.fara-labs.com/）を開き、フッターの「作者へ報告」を押します。
2. 「ロボットではありません」の確認が出て、「いまは報告を受け付けていません」の表示が**消えている**ことを確かめます（消えない場合は、1-3 の値の登録と、Turnstile のホスト名を見直します）。
3. 種類・内容を入れて送信 → Discord にメッセージ（サイト名・種類・内容・ページ）が届けば完了です。
4. 本番のサイトでも同じように 1 回確かめます。

### 困ったとき

- **「確認に失敗しました」**: Turnstile のホスト名に、そのサイトのホスト名が入っているか。シークレットキーが正しいか。
- **「送信に失敗しました」**: Discord の Webhook URL が正しいか（削除していないか）。
- **スパムが来る**: Turnstile で大半は防げますが、確実ではありません。次の「レート制限」を入れてください。それでも続くときは、Discord の該当ウェブフックを削除して作り直します（URL が変わるので、1-3 の `DISCORD_WEBHOOK_URL` も更新）。

### 1-5. レート制限（おすすめ）

短い時間に大量に送られても、Discord が受け付けなくなって、正当な報告まで失敗しないようにします。

1. Cloudflare のダッシュボード → `fara-labs.com` →「セキュリティ」→「WAF」→「レート制限ルール」→「ルールを作成」。
2. 条件: `(http.request.uri.path eq "/api/report" and http.request.method eq "POST")`
3. 「同じ特性」は IP（無料プランはこれだけ）。「レート」は**リクエスト 1・期間 10 秒**（無料プランは期間が 10 秒しか選べません）。同じ IP から 10 秒に 2 回以上送られたら、アクションの「ブロック」で止めます。「期間（ブロックを続ける時間）」も、選べる値（10 秒）を選びます（空のままだと保存できないことがあります）。
4. **式の引用符は、半角の `"` にします**（画面や文書によっては、`”` のような曲がった引用符に変わって貼り付けられ、式が正しく動かなくなります）。
5. ルール名は `report-rate-limit` など。ステータスは「アクティブ」でよいです（レート制限は、有効にしておく用途です）。無料プランのルール数には上限があります。

### 1-6. 1 日の送信回数の制限（送信元ごと 3 回まで）

1-5 の WAF とは別に、Worker の受け口（`/api/report`）が、**送信元の IP アドレスごとに 1 日（日本時間）3 回まで**数えます。4 回目は 429 になり、「1 日の送信上限（3 回）に達しました。明日もう一度お試しください。」と表示されます。

- 数えるのは、Turnstile を通ったあと、Discord に送る直前の 1 回です。Turnstile の失敗や入力の不備では数えません。Discord への送信に失敗したときは、その 1 回を戻します。
- 保存するのは、送信元の IP アドレスから作った識別子（秘密の鍵を使うハッシュ）と回数だけです。IP アドレスそのものは保存しません。識別子は、日本時間の翌日 0 時に削除されます。
- 設定はこのリポジトリに入っています（`worker/index.js` の `ReportRateLimiter` の export と、`wrangler.jsonc` の `durable_objects`・`migrations`。本番と `env.develop` の両方）。Cloudflare のダッシュボードでの作業は要りません。
- **秘密鍵（`TURNSTILE_SECRET`）を変えると、識別子がすべて変わり、回数が一度リセットされます。**
- 回数を数えられないとき（Durable Object が使えないときなど）は、制限せずに送ります（問い合わせを取りこぼさないため）。
- 仕組みの詳細は、kit の `docs/usage.md` の 2.2 を見てください。

## 2. メンテナンス画面・「更新予定」のお知らせ（Worker の変数で切り替える）

Cloudflare のダッシュボードで **変数を書き換えるだけ**で、各サイトに「更新予定」のお知らせを出したり、メンテナンス画面（503）に切り替えたりできます。サイトごと（Worker ごと）に別々に切り替えられます。対象は、ポケモン・アバター・Bot・ポートフォリオの 4 サイトです。

### 2-1. 使う変数

| 変数 | 値 | 意味 |
| --- | --- | --- |
| `MAINTENANCE_MODE` | `false`（または未設定） | 通常どおり表示（お知らせも出ない） |
| | `notice` | **通常のページの上に、「更新予定」のお知らせ**を出す |
| | `true` | **メンテナンス画面**（503）だけを出す |
| `MAINTENANCE_MESSAGE` | 文（200 文字まで） | お知らせに出す文。メンテナンス画面には「予定」として同じ文が出る（例: `10月25日（土）20:00〜21:00 ごろ、サイトを更新します`） |

- お知らせの文は、`MAINTENANCE_MODE` が `notice` または `true` のときだけ出ます。**`false` に戻せば、お知らせも一緒に消えます**（`MAINTENANCE_MESSAGE` を消す必要はありません）。
- `MAINTENANCE_MESSAGE` が空のときのお知らせは「まもなくメンテナンスを行います。」です。
- `MAINTENANCE_MODE` の値は、`true`・`on`・`1`（大文字小文字は区別しません）がメンテナンス、`notice` がお知らせです。**変数が無い・それ以外の値のときは、通常として扱います**（書き間違いでサイトが止まることはありません）。

### 2-2. 変数の登録（最初の 1 回）

1. Cloudflare のダッシュボード →「Workers & Pages」→ 対象の Worker（`fara-pokemon` / `fara-avatar` / `fara-twitch-bot` / `fara-portfolio` と、それぞれの `-dev`。本番はデプロイ後）→「設定」→「変数とシークレット」→「追加」。
2. 種類は「**テキスト**」（あとから値を見て、書き換えるため）。環境は「プロダクション」だけにチェックを付けます（プレビューは使っていません）。
3. `MAINTENANCE_MODE` = `false`、`MAINTENANCE_MESSAGE` = 空でもよい（例: 文を書いておく）。「デプロイ」。

GitHub から自動で公開（デプロイ）しても、ダッシュボードで足した変数は**消えません**（各サイトの設定に `keep_vars = true` を入れてあるため）。

### 2-3. 使い方の流れ

1. **事前のお知らせ**: `MAINTENANCE_MESSAGE` に日時を書き、`MAINTENANCE_MODE` を `notice` にして「デプロイ」→ 各ページの上に、橙色の帯で「お知らせ 〇月〇日 ... ごろ、サイトを更新します」が出ます。
2. **作業の開始**: `MAINTENANCE_MODE` を `true` にして「デプロイ」→ すべてのページがメンテナンス画面（503）になります。この間に、GitHub からの公開や、Cloudflare の手動の設定をします。
3. **完了**: `MAINTENANCE_MODE` を `false` にして「デプロイ」→ サイトが元に戻り、お知らせも消えます。

### 2-4. 反映と確認

- 「デプロイ」を押してから、数秒〜1 分ほどで反映されます（Worker はアクセスのたびに変数を読みます）。
- ポケモンのサイトは、ページを開いたときに状態を読みます。**すでに開いているタブは、再読み込みするまで変わりません。**
- ポートフォリオは、ページを開くたびに Worker が状態を見て、メンテナンス（503）にします。お知らせの帯は、アプリが起動のときに `/api/maintenance` を読んで出します（すでに開いているタブは、再読み込みするまで変わりません）。
- 確認用（`*-dev`）のサイトで先に試してください（本番に影響しません）。

### 2-5. 注意

- メンテナンス中（`true`）は、ポケモンのサイトのデータ共有（`/api/my/*`）と、**ゲームデータ（`/api/game/*`）も 503** になります（ゲームデータの更新をメンテナンス中に行えるようにするため）。配信用 BOT は、取り直しに失敗した扱いで、古いキャッシュのまま動きます（BOT にキャッシュがまだ無い初回の起動では、ゲームデータを読めずに止まります）。
- ポケモンのサイトは、ゲームデータも Worker を通すため、通常時もアクセスのたびに Worker が動きます（無料枠は 1 日 10 万リクエストです。アクセスが増えたときは、ダッシュボードの Worker の「メトリクス」で確かめてください）。
- アバターの「みんなで練習」は、すでにつながっている人の接続は切れません（新しくつなぐ人だけ 503 になります）。
- メンテナンス中は、作者への報告フォームも使えません（503）。
- メンテナンス中の画面の見た目は、[`maintenance.html`](maintenance.html) と同じ作りです。アバター・Bot・ポートフォリオは、Worker が 503 の画面を返します（ポートフォリオは、ページも API もすべて 503 です）。**ポケモンは、ページ自体は通常どおり読み込まれ（200）、そのあと、アプリが同じ見た目のメンテナンス画面を出します**（API だけが 503 です）。そのため、ポケモンでは、画面が出るまで一瞬かかり、検索エンジンへの「503」の通知にもなりません。
- 画面の文面・見た目を変えるときは、共通部品 fara-blazor-component の `worker/maintenance.js` を変更します（このリポジトリでは `external/fara-blazor-component` のサブモジュール。kit で直してタグを付け、各サイトで上げます）。
- 以前に、Cloudflare の WAF にメンテナンス用のカスタムルール（`production-maintenance` など）を作っていた場合は、削除してください（このしくみとは別のものです）。
- `worker/maintenance.js` と `worker/report.js` は、fara-blazor-component のものを import しています（このリポジトリにコピーは置きません）。
- ポートフォリオの `/api/maintenance` は、`MAINTENANCE_MODE=true` でも 200 を返します（アプリが状態を読むための入口なので、503 にしない。ページ・報告の API は 503）。
- ポートフォリオの帯は、kit の `MaintenanceBanner` がヘッダーと本文の間に出します（ページを切り替えても動きません）。Worker は HTML に帯を入れません（Blazor が画面を描き直すため）。

### 2-6. 本番の公開（GitHub Actions）との連動

本番（master）の公開（デプロイ）は、次のように動きます（4 サイトとも同じ）。

1. **公開の前に確認**: Cloudflare の Worker の変数 `MAINTENANCE_MODE` が **`notice`** になっているかを確かめます（すでに `true` のときも通します）。`false`・未設定のとき、または確認できなかったときは、**公開を止めます**（Actions に「先に MAINTENANCE_MODE を notice にしてください」と出ます）。
2. **公開と同時にメンテナンス画面**: 確認が通ったら、`MAINTENANCE_MODE=true` を付けて公開します（公開した瞬間から、メンテナンス画面になります）。`MAINTENANCE_MESSAGE` は、ダッシュボードの値のままです。
3. **作業が終わったら**: ダッシュボードで `MAINTENANCE_MODE` を `false` に戻します（お知らせも消えます）。**自動では戻しません**（作業の完了を確認してから、人が戻します）。

- 確認用（develop）の公開は、確認もメンテナンス化もしません（いつもどおり公開されます）。
- **緊急の修正を、お知らせなしで公開したいとき**: GitHub の Actions →（対象のワークフロー）→「Run workflow」で、`skip_maintenance_check` にチェックを付けて実行します（確認を飛ばし、`MAINTENANCE_MODE=true` も付けません）。**ダッシュボードの `MAINTENANCE_MODE` の値は変わらない**ので、次の点に注意してください。
  - すでに `true`（メンテナンス中）なら、公開後もメンテナンス画面のままです（公開した内容を見るには、`false` に戻します）。
  - `notice` が残っていれば、お知らせも出たままです（消すには `false` に戻します）。
- **Worker が見つからない（404）ときは止まります**（Worker 名・アカウント ID の誤りでも 404 になり、確かめたことにならないため）。**初めての公開**だけは、Deploy (production) を手動で実行し、`first_publish` にチェックを入れてください（確認を飛ばして公開します。Worker ができたら、チェックを外します）。
- メンテナンス表示の文（`maintenance_message`）は、200 文字まで・改行なしです。それを超えるとき、改行を含むときは、公開の前に止まります（Worker の変数には渡しません）。
- この確認は、Cloudflare の API で変数を読みます。**GitHub の `CLOUDFLARE_API_TOKEN` に、Workers の設定を読める権限**（公開に使っている「Workers Scripts: Edit」で足ります）が必要です。変数は「**テキスト**」にしておいてください（「シークレット」は値を読めないため、確認が止まります）。
- 公開に失敗してもメンテナンス画面のままになることがあります。そのときは、ダッシュボードで `MAINTENANCE_MODE` を確かめて、必要なら `false` に戻してください。
- **初めて本番を公開したあとに、一度だけ確かめてください**: ダッシュボードの Worker の「変数とシークレット」に、`MAINTENANCE_MESSAGE` などの変数が**残っているか**。残っていなければ、公開のたびに消える設定になっている可能性があるので、お知らせください。

### 2-7. Actions の画面（Run workflow）で切り替える

ダッシュボードを開かなくても、GitHub の Actions →「Deploy (develop)」（dev）または「Deploy (production)」（本番）→「Run workflow」で、次の入力を入れて実行すると、公開と同時に Worker の変数を設定できます（スマホの GitHub アプリからも可）。実行後は、ジョブの下部のサマリーに「設定した値」と「反映後の現在値」が出ます。

| 入力 | 意味 |
| --- | --- |
| `maintenance_mode` | `true`（メンテナンス画面）・`notice`（お知らせ帯）・`false`（通常）。空 = 変更しない |
| `maintenance_message` | お知らせ・メンテナンス画面の文（200 文字まで・改行なし）。空 = 変更しない |

- 公開されるのは、選んだブランチ（dev = `develop`、本番 = `master`）の最新のコードです。
- 本番: `maintenance_mode` を指定した実行は、公開前の確認（2-6 の 1.）を飛ばします。push と、何も指定しない実行だけが、従来どおり確認して `MAINTENANCE_MODE=true` を付けます。`maintenance_message` だけの実行は、`MAINTENANCE_MODE` を変えません（メンテナンス画面にはなりません）。
- 旧変数 `MAINTENANCE` は、もう読みません。ダッシュボードに残っていても無害なので、不要なら削除してください。
